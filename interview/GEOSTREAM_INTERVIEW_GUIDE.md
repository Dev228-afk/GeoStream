## Section A — Kafka Partitioning, Ordering, Rebalancing & Replay (`Q01`–`Q08`)

### Q01. Why partition `courier.gps.raw` strictly by `deviceId`, and what breaks if you partition round-robin?
- **30s**: Partitioning by `deviceId` routes every ping for a courier to a single partition in deterministic FIFO order, making per-device monotonic `sequence` checking and transition diffing lock-free across workers. Round-robin shuffles sequential pings across workers, creating spurious `STALE` rejections and oscillating `ENTER`/`EXIT` transitions.
- **90s**: GeoStream's state machine tracks ordered `(device_id, sequence)` transitions relative to each courier's previous fence membership. In [`internal/kafka/client.go`](../internal/kafka/client.go) (`ProduceJSONSync`), messages key strictly on `e.DeviceId` across 16 partitions. If two adjacent pings (`seq=10` inside, `seq=11` outside) went to different partitions, worker B could evaluate `seq=11` before worker A processed `seq=10`, hitting Redis `compareAdvanceLua` with out-of-order states or false sequence-gap alerts.
- **5m Deep**: `franz-go` (`kgo`) assigns partitions exclusively within a consumer group, guaranteeing single-consumer ownership per partition between rebalances. Even within a single worker pod, dispatching work by device or keeping per-partition ordered processing avoids race conditions around `lastSeenSeq[devKey]` and Redis CAS sequencing. The tradeoff is skew risk when a few depots dominate one partition (`FS-GEO-20`), which we diagnose via per-partition `geostream_kafka_lag{partition=...}`.
- **Evidence**: `run-local-001` processed `17,723` events across 16 partitions with `0` stale rejections and `0` out-of-order conflicts (`pipeline.json`).
- **Alternatives & Failure Modes**: Random/round-robin partition keys require distributed locking or stream-table joins in Flink/Kafka Streams; partition count changes alter hash modulo mappings for in-flight devices unless drained first.
- *F1.1*: How does `ProcessRecord` behave if a partition rebalance delivers an already-processed offset right after handoff? -> New owner reads durable Step 5 PG state / Step 6 Redis `LastSeq` and classifies identical `(seq, eventId, payloadHash)` as `DUPLICATE` without emitting a second transition (`6_crash_step6_to_7_replay`).
- *F1.2*: Would hashing by `(cityId, deviceId)` ever be better? -> Hashing by compound tenant/device keys helps if multi-tenant isolation or noisy-neighbor QoS is needed, as long as all pings for one `deviceId` stay on one partition.

### Q02. How does GeoStream provide at-least-once processing without claiming magical "exactly-once"?
- **30s**: We embrace Kafka at-least-once redelivery paired with deterministic idempotency in PostgreSQL and Redis: identical retries converge to the same DB row and Redis sequence without emitting duplicate transitions.
- **90s**: Kafka transactions alone cannot wrap external PostgreSQL and Redis writes cleanly. Instead, [`internal/pipeline/pipeline.go`](../internal/pipeline/pipeline.go) never commits Kafka offsets until Step 1 (DLQ ack on poison) or Step 5–6 (PG commit + Redis CAS) succeeds. On crash/redelivery, deterministic IDs (`GenerateTransitionID(runID, deviceID, fenceID, fenceVersion, seq, typ)`) and Redis Lua CAS absorb replays idempotently.
- **5m Deep**: Even the outbox relay (`PublishPendingOutbox` -> `geofence.enter` / `geofence.exit` -> `MarkOutboxPublished`) is strictly at-least-once (`7_outbox_crash_before_mark`), stamping each emitted `GeofenceTransitionV1` with the stable `transitionId` primary key so downstream consumers deduplicate cleanly.
- **Evidence**: Chaos scenarios `1_duplicate_delivery`, `5_crash_step5_to_6_replay`, `6_crash_step6_to_7_replay`, and `7_outbox_crash_before_mark` all `PASS` (`chaos-matrix.json`).
- **Alternatives & Failure Modes**: Kafka EOS (`read_committed`) only spans Kafka->Kafka topologies; claiming EOS across PG+Redis without an idempotent ledger breaks whenever Redis/PG fail independently.
- *F2.1*: Where could a downstream subscriber still see two messages? -> If the worker crashes inside `PublishPendingOutbox` after broker ack but before `MarkOutboxPublished` (scenario 7), the retry re-publishes the same `transitionId`.
- *F2.2*: How do downstream consumers deduplicate those? -> Keying/upserting by deterministic `transitionId` (plus `sourceEventId`, `sourceSequence`).

### Q03. Why choose `franz-go` (`kgo`) instead of `sarama` or `confluent-kafka-go`?
- **30s**: `franz-go` provides pure-Go (`CGO_ENABLED=0`) static Docker builds, dynamic partition pause/resume (`PauseFetchTopics`), and clean context cancellation without requiring `librdkafka` C bindings.
- **90s**: Look at [`Dockerfile`](../Dockerfile) (`CGO_ENABLED=0 go build`) and [`internal/pipeline/pipeline.go`](../internal/pipeline/pipeline.go) (`RunBoundedWorker`). Pause/resume backpressure cleanly halts broker fetches when our bounded persistence channel hits high watermark while keeping heartbeat loops healthy—critical so Kafka doesn't kick paused consumers out of the group during a slow DB pause!
- **5m Deep**: With `confluent-kafka-go`, Alpine builds require `musl` C toolchain tweaks and dynamically linked `librdkafka`. With `sarama`, group claim loops tie handler execution to session lifecycles awkwardly. `franz-go` decouples polling (`PollFetches`), pause/resume (`PauseFetchTopics`/`ResumeFetchTopics`), and explicit commit hooks (`CommitRecords`).
- **Alternatives & Failure Modes**: Using `franz-go` still requires tuning `max.poll.interval` / heartbeats if workers block synchronously without releasing poll loops; `RunBoundedWorker` runs fetch polling independently of slow DB workers.
- *F3.1*: What happens if paused topics stay paused longer than `session.timeout.ms`? -> `franz-go` keeps background consumer heartbeats alive independently of `PauseFetchTopics`, unlike consumer loops that block inside message callbacks.
- *F3.2*: Did you need `CGO_ENABLED=1` anywhere? -> Only locally on Windows for `go test -race` (race detector requirement with `gcc.exe 16.1.0`), whereas production container binaries in `Dockerfile` build statically with `CGO_ENABLED=0`.

### Q04. What happens during a Kafka consumer group rebalance or Kubernetes `SIGTERM`?
- **30s**: On `SIGTERM` (with `terminationGracePeriodSeconds: 30` in `deploy/k8s/geostream.yaml`), context cancellation stops fetching new records, drains in-flight bounded-channel work to PG+Redis, commits finished offsets, and lets Kafka reassign partitions cleanly via cooperative rebalancing.
- **90s**: Unfinished in-flight records whose PG/Redis writes did not commit remain uncommitted in Kafka and are re-read by the new partition owner. If PG *did* commit right before shutdown (`5_crash_step5_to_6_replay`), replay converges idempotently without duplicating transitions.
- **5m Deep**: During scaling events (`geostream-worker-hpa`, `minReplicas: 2`, `maxReplicas: 8`, plus `geostream-worker-pdb` `minAvailable: 1`), eager rebalances can cause brief consumer lag spikes. Prometheus alert rules monitor `geostream_kafka_lag` (`GeoStreamKafkaLagHigh` if `max > 500` for `15s`) and workers expose the `KafkaLag` gauge family—though note runtime lag polling into `KafkaLag` and `server.go`'s `"kafkaLag": 0` field are currently unwired stubs while live offset lag is computed on demand via `InspectTopicOffsets`.
- **Evidence**: Graceful drain design in `RunBoundedWorker` (`internal/pipeline/pipeline.go`); static K8s config verified via `kubectl kustomize deploy/k8s`; live multi-pod rebalance unexecuted (`BLOCKED_EXTERNAL`).
- **Alternatives & Failure Modes**: Killing pods with `SIGKILL` (grace period 0) increases duplicate replay bursts; graceful drain minimizes replay overlap.
- *F4.1*: What about `in-memory` `lastSeenSeq` in `Processor` after a rebalance? -> Because `lastSeenSeq` is an in-memory gap-detection heuristic, a newly assigned owner starts its local gap baseline at `prevSeen=0` while durable sequence monotonicity continues in Redis + PG (`effectiveFloorSeq`).
- *F4.2*: Could `pending` dwell candidates in `Engine.pending` also be lost on rebalance? -> Yes! In-memory hysteresis timers (`dwellMS > 0`) reset on partition movement unless externalized in Redis/PG—an intentional simplicity tradeoff documented in `engine.go`.

### Q05. Walk through the exact 8-step crash-safe sequence in `ProcessRecord`—why can't any two steps swap?
- **30s**: PostgreSQL commits transitions/membership/outbox at Step 5 **before** Redis advances sequence at Step 6, which happens **before** Kafka commits the offset at Step 7. Swapping Step 5 and Step 6 creates a silent data-loss window if Redis succeeds and Postgres fails.
- **90s**: Look at [`ProcessRecord`](../internal/pipeline/pipeline.go):
  1. Step 1 validates JSON/bounds (`ValidateLocationEvent`), publishing invalid payloads synchronously to `pipeline.deadletter` before acking offset.
  2. Step 2 reads Redis (`p.Redis.Read`); only `!foundInRedis` falls back to `PG.LoadMembership`.
  3. Step 3 checks `STALE` (`seq < effectiveFloorSeq`), exact `DUPLICATE`, and `CONFLICT` (`seq == LastSeq` with changed `PayloadHash` -> DLQ).
  4. Step 4 evaluates geofences (`Geo.Evaluate`). If `0` transitions, Step 6 advances Redis and commits.
  5. If transitions exist, Step 5 runs `PG.PersistTransitions` (`geofence_transitions` + `device_fence_state` + `outbox`) in one transaction.
  6. Only after PG succeeds does Step 6 call `Redis.CompareAdvance`.
  7. Step 7 commits Kafka offsets; async `PublishPendingOutbox` emits `geofence.enter` / `geofence.exit` and stamps `published_at`.
- **5m Deep**: Notice the beauty of `Step 5 -> Step 6`: if the process crashes right between `AfterPGCommit` and `CompareAdvance`, Redis still holds the *old* sequence (`seq-1`). When Kafka redelivers `seq`, Step 2 hydrates `pgLastTransitionSeq` from PG `LoadMembership`, Step 3 guards with `HasTransitionForSeq` (`pipeline.go:205`), and Step 5 `PersistTransitions` handles `pgx.ErrNoRows` on duplicate primary keys by verifying consistency inline (`SELECT ... WHERE transition_id = $1`) before Step 6 heals Redis cleanly!
- **Evidence**: `TestGate1VerticalSliceAndStep5CrashRecovery` (`step5To6CrashPGCount: 1`, `redisRecoveredInside: ["fence-004"]`) and `5_crash_step5_to_6_replay` (`PASS`).
- **Alternatives & Failure Modes**: Putting Redis first loses transitions forever because Redis suppresses the retry as `DUPLICATE` after DB rollback; dual-write fails cleanly only when the source of truth commits first.
- *F5.1*: What if `PersistTransitions` hits a primary-key conflict with DIFFERENT transition content? -> Its inline `SELECT ... WHERE transition_id = $1` check (`postgres.go:248-262`) detects field mismatches cleanly instead of swallowing conflicting inserts (`ErrConflict`).
- *F5.2*: Does `ProcessRecord` block on `PublishPendingOutbox`? -> No, `outbox` is committed atomically in PG at Step 5 so a transient Kafka produce hiccup to `geofence.enter` / `geofence.exit` never stalls core `courier.gps.raw` consumption.

### Q06. How do you replay `courier.gps.raw` or `pipeline.deadletter` safely without duplicating alerts?
- **30s**: Both replay paths flow back through the idempotent `ProcessRecord` pipeline using deterministic `transitionId` primary keys in PG and `compareAdvanceLua` sequence/hash checks in Redis, plus [`SeekGroupToEnd`](../internal/kafka/client.go) to prevent unwanted historical scans on fresh benchmark groups.
- **90s**: In [`cmd/replay`](../cmd/replay/main.go) and chaos tests (`tests/chaos/chaos_test.go`), replaying an offset window after a Step 5 or Step 6 failure preserves exact PostgreSQL transition counts (`1 == 1`). On raw event topics, `cmd/replay` increments `geostream_replay_attempts_total` and re-runs `ProcessRecord` (`cmd/replay/main.go:93-102`), whereas targeting `pipeline.deadletter` safely inspects/samples quarantined payloads (`dlqSample`, `cmd/replay/main.go:86-92`) without blindly re-injecting poisoned schema failures.
- **5m Deep**: Wait—what happens during a shared-topic multi-run benchmark like `run-local-001`? When we first ran `run-local-001` after `run-smoke-001`, a fresh consumer group starting at offset 0 re-read tens of thousands of older benchmark events! Adding `SeekGroupToEnd` before starting new simulator runs made benchmark start `O(1)` without polluting historical partitions (`FS-GEO-02`).
- **Evidence**: `5_crash_step5_to_6_replay`, `6_crash_step6_to_7_replay`, `run-local-001` (`0` duplicates, `0` stale).
- **Alternatives & Failure Modes**: Per-run dynamic Kafka topics leave orphaned topic metadata behind; explicit offset/seek control keeps cluster topology fixed.
- *F6.1*: What if you actually want to replay from a fixed historical timestamp after fixing a geofence polygon bug? -> Reset consumer group offsets to target timestamp on a recovery consumer group or feed `cmd/replay` from offset ranges; note that if `LastSeq` in Redis is higher than replayed historical sequences, intentional historical backfills require targeting a clean `runId` (or new `fenceVersion`).
- *F6.2*: Why not delete PG rows before replaying? -> GeoStream treats `geofence_transitions` as an append-only ledger (`ON DELETE RESTRICT` foreign keys in `0001_init.sql`); replays converge cleanly on a fixed state or clean `runId`.

### Q07. How do you detect and mitigate a single hot Kafka partition?
- **30s**: We register per-partition lag in `Metrics.KafkaLag` (`geostream_kafka_lag{partition="..."}`) for alert rules and expose exact partition end/committed offsets live via `/api/v1/runs/{id}/reconciliation` (`DiagnosticsPage.tsx`) so skew stands out immediately from balanced lag.
- **90s**: In [`api/server.go`](../api/server.go) and [`internal/reconciliation/reconcile.go`](../internal/reconciliation/reconcile.go) (`InspectTopicOffsets`), operators inspect live `(partition, startOffset, endOffset, committedOffset)` rows directly from Kafka/Postgres (note `Metrics.KafkaLag` and `handleRunSummary`'s `kafkaLag: 0` await wiring a periodic offset poller into Prometheus, so live diagnostics read `InspectTopicOffsets`). If one depot hashes heavily onto partition `P`, scaling pod count past 16 leaves idle consumers because Kafka restricts one partition to one group member at a time.
- **5m Deep**: True mitigation requires two layers: (a) isolate slow DB persistence per partition/worker so pausing a saturated channel or slow key doesn't stall unaffected partitions unnecessarily, and (b) increase partition count (`32`–`64`) or salt extreme hyper-active test entities (`subShard`) at producer ingest when single-key rates exceed single-goroutine serial capacity.
- **Evidence**: Per-partition offset table captured live in [`07-diagnostics-backpressure-1024.png`](../evidence/ui/screenshots/07-diagnostics-backpressure-1024.png).
- **Alternatives & Failure Modes**: Breaking per-device partition affinity fixes skew at the cost of breaking strict per-device FIFO ordering.
- *F7.1*: Why did `07-diagnostics-backpressure-1024.png` show partitions `3`, `9`, and `14` slightly ahead of committed offset? -> Because `cmd/alertdrill` produced test gap/poison events onto shared `courier.gps.raw` partitions (`3`: `5316/5304`, `9`: `5861/5857`, `14`: `5599/5592`) for its Docker worker group immediately before Playwright inspected `run-local-001`'s committed group!
- *F7.2*: Can HPA (`geostream-worker-hpa`) solve single-partition skew automatically? -> No; CPU HPA only scales replicas up to partition count (`16`), and one hot partition still binds to a single consumer instance—proving why KEDA lag-based scaling + partition capacity planning matter.

## Section B — Redis Lua CAS, Warm Cache, Eviction & Conflict Semantics (`Q09`–`Q15`)

### Q09. Why store latest device state in Redis alongside PostgreSQL, and what goes into Redis vs. Postgres?
- **30s**: Redis handles every high-frequency ping (`Lat`, `Lon`, `LastSeq`, `InsideFenceIDs`, 24h TTL) via atomic Lua CAS in microseconds, while PostgreSQL only receives rare durable state changes (`ENTER`/`EXIT` transitions, `device_fence_state`, `outbox`, `partition_checkpoints`, `incidents`).
- **90s**: In `run-local-001`, `17,723` pings produced only `3,000` transitions (`~17%`; in real production often `<5%`). Putting Redis on the hot path avoids `17,723` high-churn `UPDATE` row-locks on Postgres per run while giving `GET /runs/{id}/devices` fast `O(log N + M)` sampled reads via `ZRevRange` (`ListActiveDevices` on `ActiveKey`).
- **5m Deep**: Every cache key (`geo:<runId>:device:<deviceId>`, helper `DeviceKey`) carries a 24h TTL so stale ephemeral runs auto-expire cleanly without unbounded Redis OOM, while Postgres `geofence_transitions` and `device_fence_state` preserve durable history permanently.
- **Evidence**: `internal/redisstate/store.go` (`CompareAdvance`, `ListActiveDevices`), `migrations/0001_init.sql` (`7` tables), `run-local-001` (`1,500` active Redis keys, `3,000` PG rows).
- **Alternatives & Failure Modes**: Storing everything in PG collapses write latency under row locks (`FS-GEO-03`); storing everything in Redis loses durability on RAM eviction/restart (`8_redis_eviction_cold_recovery`).
- *F9.1*: What if Redis `EXPIRE` evicts `ActiveKey` vs `DeviceKey` inconsistently? -> Wait: `compareAdvanceLua` refreshes `EXPIRE` on both `KEYS[1]` (`device` hash) and `KEYS[2]` (`active` ZSET) inside the same atomic Lua execution (`store.go:101-114`), and `handleListDevices` (`server.go:328-330`) skips missing hashes cleanly.
- *F9.2*: Why cap `ActiveKey` cardinality (`maxActive` argument in Lua)? -> Bounds memory safety against runaway synthetic load bugs on constrained hosts.

### Q10. Explain how `compareAdvanceLua` guarantees atomic state progression without `WATCH`/`MULTI` retries.
- **30s**: Redis executes Lua scripts single-threaded and atomically, so reading `lastSeq` + `lastEventId` + `payloadHash`, comparing against the incoming ping, and writing `HSET`/`ZADD`/`EXPIRE` happen in one network round-trip with zero race windows.
- **90s**: [`compareAdvanceLua`](../internal/redisstate/store.go) evaluates: (1) if incoming `nextSeq < existingSeq` (or `< minSeqFloor`), return `"STALE"`; (2) if `nextSeq == existingSeq` and `lastEventId == nextEventId && payloadHash == nextPayloadHash`, return `"DUPLICATE"`; (3) if equal seq with changed hash, return `"CONFLICT"`; (4) otherwise atomically update all hash fields (`lastSeq`, `lastEventId`, `payloadHash`, `lat`, `lon`, `insideFenceIds`, etc.), score `ZADD` with `nowMs`, refresh TTL, and return `"ACCEPTED"`.
- **5m Deep**: Using `WATCH`/`MULTI`/`EXEC` under concurrent replay requires retry loops whenever a key changes between `GET` and `EXEC`, adding tail latency spikes on hot keys. Moving the state guard into Lua keeps CAS O(1) and predictable. Note that `ProcessRecord` still checks Step 3 before Step 5 so invalid/conflicting pings are routed to DLQ *before* hitting DB transactions.
- **Evidence**: `TestRedisAtomicLuaCompareAdvanceAndConcurrency` passing under `go test -race`.
- **Alternatives & Failure Modes**: Client-side locks (Redlock) add extra round trips and lease-expiry corner cases; Lua errors fail closed as `ErrTransientRedis`.
- *F10.1*: Isn't Redis single-threaded execution a bottleneck for Lua scripts? -> Only if Lua scans collections (`KEYS`, huge loops). `compareAdvanceLua` performs strictly O(1) hash `HGET`/`HSET` + one `ZADD` (O(log N) on ZSET) in microseconds.
- *F10.2*: Why pass `minSeqFloor` into Lua too? -> Ensures even if Redis was cold-missed (`!foundInRedis`) and hydrated from PG `pgLastTransitionSeq`, a stale ping can't sneak past CAS concurrently.

### Q11. How do you distinguish `DUPLICATE`, `STALE`, and `CONFLICT`—especially when GPS timestamps arrive out of order?
- **30s**: `STALE` means `seq < latest`, `DUPLICATE` means identical `seq`, `eventId`, and SHA-256 `payloadHash`, and `CONFLICT` means equal `seq` with mutated coordinates/payload (quarantined to DLQ). Monotonic ordering keys on `sequence` (`int64`), NOT noisy device wall-clock `eventTime`.
- **90s**: Mobile GPS chipsets experience NTP clock skew (`AllowedSkew`), so comparing wall timestamps drops valid sequential transitions. In [`internal/schema/validate.go`](../internal/schema/validate.go) (`CanonicalEventPayloadHash`) and `ProcessRecord`, per-device `sequence` governs state progression while timestamps stay observable metadata inside `geofence_transitions.event_time`.

### Q27. How does context cancellation propagate safely through Kafka fetchers, Postgres transactions, and HTTP SSE streams?
- **30s**: Every blocking I/O boundary—Kafka `PollFetches` / `ProduceJSONSync`, Postgres `Begin`/`Exec`, Redis `Eval`, and API handlers `r.Context()`—accepts Go `context.Context`, returning promptly on `SIGTERM` or client tab disconnect without leaking goroutines.

Similarly, [`RunBoundedWorker`](../internal/pipeline/pipeline.go) propagates context cancellation down to worker drains and graceful consumer closure.

- **Evidence**: `api/server.go:612-615`, `internal/storage/postgres.go:156`.

### Q28. When would you batch PostgreSQL transition writes vs. committing per transition event?
- **30s**: GeoStream currently executes one atomic transaction per transition-producing event (`PersistTransitions`) for strict Step 5->6 causal accuracy (`50 ms` p99 locally); at `80,000 events/s` cluster targets (`1–5%` transitions = `800–4,000` tx/s), micro-batching `10`–`50` transitions per tx cuts WAL `fsync` overhead 10–50× at the cost of holding offsets briefly until batch commit.
- **90s**: Today's per-event transaction commits `geofence_transitions`, `device_fence_state`, and `outbox` together, making `5_crash_step5_to_6_replay` and offset mapping trivial per record (`p50=12 ms`, `p95=20 ms`, `p99=50 ms` locally). If PG WAL sync (`synchronous_commit`) caps single-host writes around ~1–2K tx/s under burst transitions, micro-batching independent devices within a 5–10 ms linger window amortizes network RTT + WAL flush across dozens of devices while still honoring `Step 5 -> Step 6 -> Step 7` for the whole batch!
- **5m Deep**: Notice batching *across* distinct devices is safe because each `(run_id, device_id, fence_id, fence_version)` row is independent; however, Step 6 Redis Lua CAS updates for each item in the batch must wait until the shared batch PG transaction commits cleanly (`commit` -> pipeline Redis CAS scripts -> commit highest offsets per partition).
- **Evidence**: `run-local-001` achieved `3,000` PG transition commits cleanly in ~12s with `0` pending outbox rows (`PIPELINE_TRANSITION p50=12 ms`).
- **Alternatives & Failure Modes**: Unbounded micro-batch linger adds tail latency directly onto `PIPELINE_TRANSITION p99` and increases duplicate replay blast radius on crash.
- *F28.1*: Why didn't `run-local-001` hit a WAL crisis at `3,000` transitions? -> Only `3,000` out of `17,723` events crossed geofences (~`250` tx/s over 12s), well within local PG capacity once warm-path `LoadMembership` queries were removed (`FS-GEO-03`).
- *F28.2*: How would you handle a single conflict row failing a batched PG transaction? -> Fall back to per-item persistence on conflict error so one poison sequence doesn't poison an entire clean micro-batch.

### Q29. What deadlocks or memory leaks can happen in Go pipeline workers, and how do GeoStream patterns prevent them?
- **30s**: Classic Go pitfalls are unclosed channels stalling worker shutdown, mutex hold across network I/O, and unbounded maps keyed by `deviceId`. GeoStream keeps `Processor.mu` strictly around tiny in-memory map/counter updates, avoids network calls under locks, bounds Redis keys with 24h TTL + `maxActive`, and drives goroutines via `context.Context`.
- **90s**: Check `internal/pipeline/pipeline.go:164-173`: `p.mu.Lock()` reads/updates `p.lastSeenSeq` and unlocks immediately *before* touching Postgres, Redis, or Kafka. Look at `Engine.mu` in `engine.go:60`: held strictly around `pending` map timestamp arithmetic, never across external I/O. And bounded channels isolate slow DB pools cleanly without spawning leak-prone detached goroutines.
- **5m Deep**: One scaling nuance worth calling out proactively in interviews: `Processor.lastSeenSeq` (`map[string]int64`) currently grows O(unique devices in process memory). At `40,000` devices (`~40,000 * ~40 bytes`), it's under `5 MB`, negligible; at `10M+` unique devices over months of uptime, we would evict idle `lastSeenSeq` entries via LRU or move gap state periodically after partition revocations.

- *F29.2*: Why lock `device_fence_state` deterministically by `(run_id, device_id, fence_id, fence_version)` PK? -> Per-device Kafka partition affinity means only one worker writes a given `(run_id, device_id)` row at a time, eliminating cross-worker PG row deadlocks altogether.

### Q30. Walk through GeoStream's 7 canonical PostgreSQL tables (`migrations/0001_init.sql`) and why each exists.

Partial indexing on `WHERE published_at IS NULL` keeps background `FetchPendingOutbox` queries O(pending) (`~0` rows at steady state) even when `geofence_transitions` holds millions of published historical records!
- **Evidence**: Clean execution across integration, chaos (`10/10`), and live alert drills (`OverviewPage` Operational Incidents table).
- **Alternatives & Failure Modes**: Storing raw pings in PG forces multi-terabyte table bloat (`Q33`); omitting `idx_outbox_pending` partial index turns every relay poll into a seq-scan at scale.

- *F30.2*: Why compound `(event_time DESC, transition_id DESC)` on `idx_gt_run_time_id`? -> Enables keyset cursor pagination in `ListTransitions` (`TransitionsPage.tsx` `Next page ->`) without slow `OFFSET N` scans.

### Q31. Explain `PersistTransitions` idempotency and outbox publishing under partial DB/Kafka failures.

If downstream transition topics experience a broker leader election during maintenance, `outboxPending` temporarily ticks up while `courier.gps.raw` ingestion continues unimpeded!
- **5m Deep**: In `7_outbox_crash_before_mark`, `FaultHooks.AfterOutboxPublish` intentionally aborts the worker *right after* `ProduceJSONSync` delivers `GeofenceTransitionV1` to Kafka and *before* `MarkOutboxPublished` sets `published_at`. ### Q32. Why did `PostgresStore.Migrate` need `pg_advisory_xact_lock(727001)`?
- **30s**: Running Go test suites executes packages (`api`, `tests/integration`, `tests/chaos`) concurrently in separate OS processes; without an advisory transaction lock, parallel `CREATE TABLE IF NOT EXISTS` calls collide inside PostgreSQL's `pg_type` catalog with `SQLSTATE 23505`.
- **90s**: Many developers assume `CREATE TABLE IF NOT EXISTS` in SQL is concurrency-safe because "IF NOT EXISTS" sounds atomic. In Postgres, checking existence and inserting catalog rows across two concurrent transactions racing first-time table creation throws `duplicate key value violates unique constraint "pg_type_typname_nsp_index"`. Acquiring `SELECT pg_advisory_xact_lock(727001)` serializes migration DDL cleanly at transaction granularity (`FS-GEO-01`).
- **5m Deep**: Because the lock is *transaction-scoped* (`pg_advisory_xact_lock`), PostgreSQL releases it automatically on commit or rollback even if a pod panics—unlike session-level advisory locks (`pg_advisory_lock`) which risk dangling locks under PgBouncer transaction pooling.
- **Evidence**: Zero `SQLSTATE 23505` errors across concurrent `go test -race ./internal/... ./api/... ./tests/...` executions (`task-1478`).
- **Alternatives & Failure Modes**: Disabling Go parallel package testing (`-p 1`) masks the bug in dev while failing rolling multi-pod startup in K8s (`replicas: 2`).
- *F32.1*: What if future schema adds `0002_*.sql` backward-incompatible migrations? -> Move from pure `IF NOT EXISTS` scripts to a versioned `schema_migrations` table guarded by the exact same `pg_advisory_xact_lock(727001)`.
- *F32.2*: Why choose numeric key `727001` instead of locking an application table? -> Advisory locks work before any schema table even exists on an empty fresh database (`pg_advisory_xact_lock` requires zero pre-created objects).

### Q33. Why NOT write every GPS ping directly to PostgreSQL?
- **30s**: At `80,000` GPS pings/sec (`TARGET`), writing every ping to Postgres would burn ~80K WAL-logged `INSERT`/`UPDATE` IOPS/s for mostly redundant movement inside or outside polygons, whereas gating through Redis + GeofenceEngine writes only rare transitions (`~1–5%`) to Postgres (`800`–`4,000` tx/s).
- **90s**: We even observed this empirically on single-host Docker (`FS-GEO-03`): merely executing an extra read `PG.LoadMembership` on warm pings drove `PIPELINE_TRANSITION p99` to `500 ms`; removing warm pings from PG dropped p99 to `50 ms`! Even in `run-local-001`, `17,723` raw pings compressed into `3,000` durable transitions (~`83%` write amplification eliminated).
- **5m Deep**: Additionally, Kafka *itself* is already the durable raw ping log for retention windows (hours/days). If raw historical trajectories are ever needed for offline ML/analytics, batch-compacting Kafka -> S3/Parquet asynchronously beats hammering an OLTP row store with every half-second lat/lon ping.
- **Evidence**: `run-local-001` (`17,723` consumed -> `3,000` PG transitions, `500ms -> 50ms` after warm-path fix).
- **Alternatives & Failure Modes**: Storing raw pings directly in Postgres TimescaleDB adds ingest CPU/storage costs 20–100× over Redis+transition storage when operational state only needs current location + crossings.
- *F33.1*: What if an auditor demands raw breadcrumbs for dispute resolution? -> Tap a separate Kafka consumer group (`analytics-sink`) writing batch-compressed Parquet/JSONL objects directly from `courier.gps.raw` to S3 cleanly off the real-time ingest hot path!
- *F33.2*: Does skipping raw-ping SQL storage lose replayability? -> No: Kafka retains raw ping logs natively for the operational retention window, while `device_fence_state` + `geofence_transitions` + `outbox` hold all state-machine truth durably in Postgres.

### Q34. What happens if PostgreSQL suffers a brief outage while Kafka and Redis remain healthy (`9_transient_db_outage_retry`)?
- **30s**: Because Step 5 (PG) runs *before* Step 6 (Redis CAS) and Step 7 (Kafka commit), `BeforeDBWrite` failure returns `ErrTransientDB`, aborts cleanly before mutating Redis, increments `geostream_db_worker_errors_total`, and holds Kafka offsets uncommitted until PG recovers and retry converges cleanly.

Meanwhile, if the DB outage lasts long enough to fill `GEOSTREAM_CHANNEL_CAP=4096`, `RunBoundedWorker` pauses Kafka topic fetching (`PauseFetchTopics`) so memory stays flat while Postgres recovers.
- **5m Deep**: Compare that cleanly against a naive Redis-first worker: during a 10-second PG outage, naive workers advance `LastSeq` in Redis across hundreds of transition events, drop all PG writes on error, and then suppress Kafka's redeliveries as `DUPLICATE` when PG comes back!
- **Evidence**: `chaos-matrix.json` scenario `9_transient_db_outage_retry` (`pgRows: 1`, `redisSeq: 1`, `reconcilePass: true`, `PASS`).
- **Alternatives & Failure Modes**: Writing failed transitions to a local file/queue invites split-brain ordering errors if a worker restarts with ephemeral pod disk; halting on Kafka offsets preserves cluster durability.

- *F34.2*: How fast does the worker recover once PG restarts? -> As soon as `PersistTransitions` stops failing, in-flight retry drains pending buffered items, `ResumeFetchTopics` re-enables Kafka fetching, and Step 6 heals Redis incrementally.

### Q35. How does `cmd/reconcile` (`AuditRun`) verify end-to-end ledger integrity and catch silent gaps?
